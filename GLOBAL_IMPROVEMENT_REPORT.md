# Итоговый отчёт: глобальное улучшение KopilkaMoto (v6.6 → v6.8)

Дата: 19.11.2026. Аудит и план — в `GLOBAL_AUDIT.md`. Все цифры получены реальными прогонами (Node 22, Chromium Playwright 1.63, Lighthouse 12).

## Что выбрано и почему

Аудит показал, что проект в хорошем состоянии (Lighthouse 98/100/100/100, axe — 0 нарушений, `npm audit` — 0). Придумывать проблемы не стали: выбрали три направления с наибольшим долгосрочным эффектом.

| Направление | Почему |
| --- | --- |
| Безопасность | Защита от XSS держалась на дисциплине, а не на механизме: будущая правка с `innerHTML` прошла бы молча |
| Тестирование | Интерфейс (57% всего JS) не имел измеряемого порога покрытия; регрессии в нём не были бы замечены |
| Архитектура | `app.js` — монолит на 1480 строк с изменяемыми глобальными переменными: каждая новая функция делала его хуже |

## Как это проверено

- `npm run lint && npm test && npm run build` — без ошибок: lint OK; 66 unit; порог покрытия unit OK; 65 E2E; порог покрытия E2E OK; сборка OK.
- Обратная совместимость данных: формат `moto-tracker-v1` и миграции из `moto-savings-tracker` не затронуты (`core.js` и `storage.js` не менялись), тесты миграций и копий v1 проходят.
- Офлайн-режим: E2E «офлайн-запуск и обновление по кнопке» и «собранный сайт» проходят, в офлайн-кеш попадают все 26 файлов (тест сравнивает список с папкой `js/**`).
- Разделение `app.js` — перенос функций без переписывания: все 58 прежних E2E прошли без единой правки.

## Что поймали по ходу (и исправили)

1. **Trusted Types сломали регистрацию service worker** (`register()` — тоже опасный приёмник) — офлайн-режим пропал бы. Нашли тесты `pwa`/`build`/`smoke`; добавлена единственная политика для адреса `./service-worker.js` и тест на неё.
2. **Сбор покрытия терял данные** при перезагрузке страницы (V8 выбрасывает покрытие старого документа) — отчёт показывал, что вызванные функции не вызывались. Покрытие теперь сбрасывается перед перезагрузкой; для перезагрузок, которые делает само приложение, — `flushCoverage`.
3. **Порог покрытия сразу показал пробелы**: не тестировались успешное сохранение цели и сроков, сохранение адреса прокси, кнопки «Скачать»/«Удалить» у сохранённых копий, установка приложения, баннеры напоминаний, недоступное хранилище. Добавлены 7 E2E-сценариев; порог не снижали.
4. **Замер Lighthouse на локальном HTTP/1.1 показал ложную регрессию** (98 → 94, LCP 2,3 → 2,9 с) из-за 26 запросов. Проверка по HTTP/2 в одинаковых условиях: регрессии нет (99, LCP 2,1 с). Для всех модулей добавлены `modulepreload`, тест следит за их полнотой.
5. **В `main` приехала копия проекта** в подпапке `KopilkaMoto-main/` (при загрузке архива) — версия 6.6.2 не попадала на сайт, CI был красным. Правки перенесены в настоящие файлы, подпапка удалена.

## Что осталось за рамками и почему

| Что | Почему не сделано |
| --- | --- |
| Минификация JS/CSS (≈ 20 КБ по Lighthouse) | Потребует шага сборки или бандлера; проект намеренно работает без них. Выигрыш — единицы процентов |
| Trusted Types в Safari и Firefox | Не поддерживаются браузерами; там остаётся прежняя защита — строгая CSP и DOM без HTML-строк |
| Проверка на реальных Android и iPhone | Недоступно из среды разработки; чек-лист в `QA_REPORT.md` |
| Развёртывание Cloudflare Worker | Нужны ваши учётные данные; инструкция в README |
| Разбиение `core.js` (764 строки) | Чистый модуль без DOM и состояния, покрытие 96,9%; разбиение сейчас не даёт эффекта |

## Рекомендации

1. **Хранить правки только в файлах репозитория.** Загрузка папки из архива создаёт копию внутри проекта (случилось дважды).
2. **Новые экраны добавлять модулем `js/ui/<имя>.js`** и регистрировать в `js/ui/pages.js` — тесты сами потребуют добавить файл в офлайн-кеш и `modulepreload`, не допустят цикла и файла длиннее 400 строк.
3. **Если приложение вырастет**, первым шагом выделить из `core.js` расчёты (прогноз, отметки, разбивка расходов) в `js/domain/*` по тому же принципу.
4. **Проверить приложение вручную в Safari/Firefox** (там нет Trusted Types) и на телефонах по чек-листу.
5. **Рассмотреть CI-шаг Lighthouse** с порогом, чтобы регрессии производительности ловились автоматически (замер лучше делать по HTTP/2).
