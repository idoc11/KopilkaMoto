## 2. Выявленные проблемы

### Архитектура — **важно**

| # | Проблема | Факты |
| --- | --- | --- |
| A1 | `js/app.js` — монолит | 1490 строк, 53 КБ, 64 функции, 14 разделов (навигация, главная, форма, история, частые расходы, онбординг, настройки, копии, AI, SW, синхронизация…) в одном файле |
| A2 | Скрытая связанность через изменяемые глобальные переменные | `state` — 42 обращения, `prefs` — 57, `ui.*` — 81; любой раздел может менять что угодно, зависимости не видны из импортов |
| A3 | Каждая новая функция увеличивает монолит | За последние версии `app.js` вырос примерно с 1100 до 1490 строк (частые расходы, замок, «Куда ушли деньги») |

### Безопасность — **важно**

| # | Проблема | Факты |
| --- | --- | --- |
| S1 | Защита от DOM-XSS держится на дисциплине, а не на механизме | Опасных приёмников (`innerHTML`, `eval`…) в коде нет, но CSP не включает Trusted Types — будущая правка с `innerHTML` пройдёт молча |
| S2 | `img-src` шире нужного | Разрешены `data:` и `blob:`, хотя приложение не показывает картинок из этих источников |
| S3 | Генератор DOM `h()` записывает любые атрибуты без проверки | Сейчас `href` получает только `blob:` и `location.href`, но защиты от `javascript:` нет |
| S4 | Нет регрессионных тестов самой CSP | Тесты ловят нарушения CSP в консоли, но не проверяют, что CSP блокирует инлайн-скрипт, `eval` и запись HTML |

Сделано раньше и подтверждено аудитом: строгая CSP без `unsafe-inline`, защита от кликджекинга, безопасный Markdown, лимиты в Worker, `npm audit` — 0.

## 3. План (3 задачи)

Выбраны направления **безопасность**, **тестирование и CI** и **архитектура**. Порядок выбран так, чтобы перед рефакторингом уже стояла защитная сетка.

### Задача 1. Механическая защита от XSS (S1–S4)
- **Цель:** CSP с Trusted Types (`require-trusted-types-for 'script'; trusted-types 'none'`); `img-src 'self'`; проверка URL в `h()`; регрессионные E2E-тесты CSP: запись HTML, инлайн-скрипт, `eval`, `javascript:`-ссылки блокируются.
- **Файлы:** `index.html`, `js/app.js`, `tests/e2e/security.test.mjs`, `tests/unit/shell.test.mjs`.
- **Проверка:** новые тесты падают без изменений и проходят с ними; axe и все E2E зелёные.
- **Риски:** axe-core или Playwright могут использовать запрещённые приёмники в странице — проверить сразу; Safari и Firefox не поддерживают Trusted Types — там остаётся текущая защита.

### Задача 2. Измеряемое покрытие UI-слоя (T1)
- **Цель:** постоянный сбор V8-покрытия JS в E2E (`npm run test:e2e:coverage`), отчёт по каждому файлу `js/**`, порог ≥ 80% байтов для каждого UI-модуля; шаг в CI.
- **Файлы:** `tests/e2e/helpers.mjs`, `scripts/e2e-coverage.mjs`, `package.json`, `.github/workflows/ci.yml`.
- **Проверка:** отчёт с цифрами по файлам; при искусственно завышенном пороге проверка падает.
- **Риски:** замедление E2E — замерить; сбор только в Chromium (достаточно для порога).

### Задача 3. Разделение `app.js` на модули интерфейса (A1–A3)
- **Цель:** `app.js` ≤ 150 строк (только инициализация); UI разнесён по модулям `js/ui/*` до 400 строк каждый; общее изменяемое состояние — один явный объект `app` в `js/ui/context.js`, зависимости видны из импортов. Без изменения поведения.
- **Файлы:** `js/app.js`, новые `js/ui/*.js`, `service-worker.js` (SHELL), `index.html` (`modulepreload`), `tests/unit/shell.test.mjs` (проверка `js/**`), `eslint.config.js`.
- **Проверка:** все 54 E2E и axe без изменений; покрытие UI-модулей по задаче 2 ≥ 80%; размеры модулей; офлайн-тест и тест сборки.
- **Риски:** регрессии при переносе — снижаются E2E-покрытием ~85% и переносом без переписывания логики; циклические импорты — допустимы для функций, проверяются запуском; старые кеши SW — поднять версию.
